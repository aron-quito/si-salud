  2. PROCEDIMIENTO DE DESPLIEGUE EN MOTOR MYSQL 8.X
================================================================================

Requisito: Servidor MySQL 8.0+ (o MariaDB 10.6+) en ejecución local o contenedor.

Método A: Ejecución mediante MySQL Workbench
─────────────────────────────────────────────
  1. Iniciar sesión en su instancia local de MySQL.
  2. Menú: File > Open SQL Script...
  3. Seleccionar el archivo:
     01_Base_de_Datos_MySQL/si_salud_database_completa.sql
  4. Ejecutar el script completo (Ctrl+Shift+Enter / Cmd+Shift+Enter).
  5. En el panel de esquemas aparecerá la base `si_salud` con 16 tablas InnoDB.

Método B: Ejecución vía Terminal o Docker
──────────────────────────────────────────
  mysql --default-character-set=utf8mb4 -u root -p < 01_Base_de_Datos_MySQL/si_salud_database_completa.sql

Consultas de verificación inmediata:
────────────────────────────────────
  USE si_salud;
  SHOW TABLES;                              -- Debe listar exactamente 16 tablas
  SELECT COUNT(*) FROM USUARIO;             -- Retorna 10 usuarios semilla
  SELECT COUNT(*) FROM BLOQUE_HORARIO;      -- Retorna 32 bloques de agenda
  SELECT fn_calcular_edad('1990-03-15');   -- Retorna 36 años
  SELECT fn_verificar_slot_libre(1);        -- Retorna 1 (Slot disponible)

  3. PROTOCOLO DE VALIDACIÓN TRANSACCIONAL (PROCEDIMIENTOS Y FUNCIONES)
================================================================================

El archivo `01_Base_de_Datos_MySQL/pruebas_procedimientos_mysql.txt` contiene
la batería de pruebas para comprobar la solidez de las reglas de negocio:

  • Escenario 0: Verificación de instalación, tablas y funciones deterministas.
  • Escenario 1: Generación masiva de agenda (sp_crear_bloques_horarios) y
                 reserva concurrente con bloqueo pesimista (sp_registrar_cita_medica).
  • Escenario 2: Prueba de concurrencia y prevención de doble reserva
                 (retorna código -1 y mensaje controlado 'Error: Slot no disponible').
  • Escenario 3: Cancelación reactiva (sp_cancelar_cita_reactiva), liberación
                 inmediata del bloque y auditoría en LISTA_ESPERA.
  • Escenario 4: Política anti-abuso (sp_reprogramar_cita): permite hasta 3
                 reprogramaciones; al 4to intento suspende la cuenta a 'Bloqueado'.
  • Escenario 5: Check-in presencial en recepción (sp_registrar_asistencia_ticket):
                 emisión correlativa de ticket (C-00X) con garantía de idempotencia.
  • Escenario 6: Auditoría y reporte consolidado multi-tabla del sistema.

Nota: Los escenarios pueden ejecutarse bloque a bloque en MySQL Workbench o
de manera automatizada en un clic desde el panel de Administración del MVP.

================================================================================
  7. FUNDAMENTACIÓN TÉCNICA Y DECISIONES DE ARQUITECTURA
================================================================================

  1. Control de Concurrencia y Bloqueo Pesimista:
     Para prevenir el doble agendamiento en accesos simultáneos, se ejecuta:
     `SELECT estado FROM BLOQUE_HORARIO WHERE id = p_bloque_id FOR UPDATE;`
     dentro de una transacción serializable. Esto otorga exclusividad sobre
     el registro hasta el cierre de la transacción, evitando condiciones de carrera.

  2. Política de Tolerancia y Anti-Abuso:
     Toda solicitud de reprogramación audita la transacción en la tabla
     `HISTORIAL_REPROGRAMACION`. Al alcanzar el límite estricto de 3 reprogramaciones
     asociadas a la cita, el procedimiento actualiza de forma autónoma el estado
     del usuario a 'Bloqueado', restringiendo futuras operaciones.

  3. Idempotencia en la Emisión de Tickets de Turno:
     El procedimiento `sp_registrar_asistencia_ticket` verifica previamente si ya
     existe un ticket generado para la cita. En caso afirmativo, devuelve el código
     existente sin crear duplicidades ni alterar el correlativo del sistema.
